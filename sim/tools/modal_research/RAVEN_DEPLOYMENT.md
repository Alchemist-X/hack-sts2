# Raven controller and Modal workers

Use a single Raven controller for the first deployment. Keep SQLite and all submit/admission state on Raven's local ext4 filesystem. Deploy Modal GPU functions only after a separate acceptance run. The existing five-minute Modal tick declaration is an alternative for a future transactional backend. In this topology install a Raven timer and leave the Modal schedule disabled. Run all work in a new project-owned service directory under `/data/raven/hack-sts2-modal-research` and the workspace's own Modal environment. Keep the Claude service, run directories, weights, trajectory data and human game saves outside the image and mounts.

## 1. Workload identities and installation

1. Check out the reviewed code by full commit into an isolated Raven service directory. Install the scheduler in a dedicated environment and bind the operational ledger to its local disk. Initialize it from the existing approvals/reserves under one controller owner. Import or migrate the database transactionally, check its integrity and verify that the old controller is inactive before enabling the timer. Keep an access-controlled backup of each migration.
2. Produce a pinned Linux GPU image from this branch's environment source and Python dependencies. Independently hash the image inputs, NativeAOT library, the library's raw observation schema, and the dependency lock. If reusing a NativeAOT artifact, verify its source tree and ABI first. Include only code, environment assets and frozen seed manifests. Use a fresh Volume v2 for project artifacts, partitioned by study and job. The approved capacity worker requests `H100!`, 16 CPU cores, 65536 MiB and explicit limits. Use a shorter Function timeout and smaller environment batch for the initial independently authorized smoke.
3. Give the Raven project service a Modal workload identity authorized to spawn and reconcile this project's functions, with the project's own deployment/Volume permissions granted to a deployment identity. Inject a distinct restricted worker credential into Modal. Store signing/transport credentials in team-managed bindings. Keep bearer tokens and signing material outside SQLite, Git and artifacts. The audited Modal member profile established workspace metadata reads only. The audited Raven team launcher established CLI startup and a model entitlement error. Neither establishes these workload permissions.
4. For worker-to-Raven admission, put a tiny HTTPS broker on Raven loopback and expose it only to a project-tagged tailnet worker identity using an approved private tailnet Serve route. Modal containers can use a userspace Tailscale HTTP proxy with an ephemeral tag-scoped enrollment credential. Restrict the ACL to one broker port and keep broker request authentication separate from network access. The team must provide or approve an existing equivalent private route, a project ACL grant, and service credentials. Verify connectivity with a bounded CPU request before building or launching a GPU worker. Do not use a publicly accessible listener or reuse a personal login session. If the private route is unavailable, leave deployment disabled.

## 2. Durable dispatch and admission

Implement the following in the Raven process sharing the same transactional ledger. A worker never opens SQLite over the network.

- The controller starts a tick under a SQLite lease. Its backend's submit validates the live controller fence, deadline, state version, budgets and stop marker in the same transaction that inserts the broker job keyed by `Job.key`. Its deterministic broker ID is a durable receipt even if the controller process dies before attaching it. Lookup checks the broker ledger. The ledger forbids acceptance from stale fences and returns authoritative absence only after fencing stale submitters.
- A Raven dispatcher atomically claims one broker job and marks its provider attempt `spawning` before calling Modal `spawn`. Include a random launch nonce bound to the study, attempt, kind and immutable config hash. Record the returned Modal FunctionCall ID and poll that exact call from successive ticks. A lost spawn receipt leaves the attempt ambiguous. Match a later worker callback against the nonce and reconcile against the provider's input ID or call records. If ambiguous through the deadline, retain the reserve and stop new submissions. Do not invoke `spawn` again for that attempt based on the absence of a receipt.
- The worker calls broker `claim` before importing Torch or opening a checkpoint. Authenticated request includes the launch nonce, expected study/attempt, Modal input ID and fresh invocation UUID. In one transaction, broker checks launch eligibility and reserves the only permitted execution lease with a monotonically increasing fencing generation. It returns the frozen packet and an accepted-checkpoint proof when applicable. Worker fetches no free-form URLs, input directories or user paths. The lease grant is short-lived and bound to the invocation. A duplicate invocation gets a rejection and records only its bounded startup overhead.
- Broker renews the lease and spend window at heartbeats from the same invocation and fences result/generation writes. Worker watchdog ends the trainer if it loses the grant and exits within the previously admitted hard deadline and spend window. Confirm termination or wait until the earlier worker's bounded grant plus kill grace has elapsed before admitting a new invocation. Use the provider input ID and invocation UUID to distinguish preemption restarts. Revoke stale claims after actual worker departure or expiry, then recheck both resource and retry limits before further GPU work. Set Modal retries to zero and retain the in-worker preemption guard because Modal may restart interrupted inputs independently.
- When the worker publishes a generation, allocate its immutable directory from the current lease generation plus a unique identifier. Publish/checksum payload files, commit, publish/checksum ready marker, commit again, then report the manifest reference to the broker. Reject late publication from an expired fence even if its files exist. Reconcile elapsed/startup/GPU/CPU/storage/egress and all attempts. Retain reserves when platform cost remains unknown. Do not treat provider receipt loss, rejection by a worker, or container reclamation as free.

## 3. Worker and agent jobs

- Bind both Modal functions to the guarded `native_worker.run` path. The GPU process resolves dependencies and seed artifacts from the pinned image. Fresh jobs enter PPO at decision zero from random initialization. Resume reads only the verified checkpoint role selected by the broker's accepted current head. Keep all capacities' seed cursors and result generations separate. They may use identical environment seed schedules for paired comparisons. Pin the actual rollout-aligned decisions for each milestone.
- Finish the trusted worker supervisor and artifact adapter. Run the trainer under an external deadline watchdog, with a periodic callback after the trainer's atomic checkpoint write to publish a complete generation. The trainer checkpoint bundles model/optimizer/RNG/seed-stream state. The artifact adapter supplies the component evidence, a scheduler descriptor for this fixed-LR recipe and the checksummed metrics. Verify the selected build's resume fields and verify Volume v2 publication on the real worker. Evaluation must write per-seed outcomes from the frozen dev seedset, using full fresh greedy play with breaker and search disabled. Keep blind evaluation behind a separately frozen release.
- Research and SOL are distinct Raven job types. Use a constrained Raven process launcher rather than a model string as a job adapter. Atomically acquire each local job row before start, persist process group ID, Codex session ID, timestamps and stderr/output metadata, require a terminal event and schema-valid final response. Bound stdout/stderr at the reader, not with process-wide file size limits. Run SOL in an isolated writable checkout with approved test commands and a fixed deadline. Verify file changes and an actual test call before considering its probe successful. Validate both roles' authorized model identity and fail closed on unresolved cost or an unsupported model.

## 4. Release order

Run a CPU-only deployment probe against a test ledger to verify private admission, stop/fence behavior, restart and duplicated requests. Exercise a deliberately lost provider receipt without a second effective worker. Provision a bounded GPU acceptance task only after that passes and a dedicated GPU reserve is recorded. Verify training, committed checkpoint, interrupted recovery, full fresh evaluation, then a decision using the actual new result. Finally disconnect the initiating terminal, restart the Raven service once and show it creates the next authorized job and charges the original ledger. Enable the timer for capacity experiments after these gates and a current account limit check.

Current implementation includes the local transaction reducer, lineage preflight and guarded trainer/evaluator call. Private broker endpoints, service supervision, per-attempt Modal reconciliation and volume publication adapter are production integration work. There is currently no live controller, admitted GPU experiment or confirmed team SOL model binding in this module.
