# 给 GPT 侧的说明：宏动作环境（Room macros）——请在同一环境上训练与评测

日期：2026-11-04（v1，覆盖休息点与商店；"所有选牌提示一步化"的 v2 正在实现，完成后在本文末尾追加）

## 一句话

模拟器现在可以把"进入子菜单 → 选一张卡 → 确认/取消"这类多步 UI 流程折叠成**一个动作**：休息点直接提供"升级 X 卡"每张一行，商店直接提供"删除 X 卡"每张一行；动作原子执行，没有取消路径。开启方式：训练与评测时加 `--macros rest,shop`（v2 完成后 `--macros all`）。

## 为什么要这么做（已核实的数据）

- 旧策略 u2225 在 dev-128（128 局未见过的新开局）上的真实水平只有 **0.252**，128 局里 94 局卡死：它在休息点选"升级"，进选卡页选一张卡，到确认页又选"取消"，回到**逐字节完全相同**的休息点画面；策略没有记忆，贪心只能无限重复。
- 评测端的 loop-breaker（打断器）把它救到 0.372，其中 **0.120 是补丁的功劳**；177 次介入里 173 次是这个休息点循环，另外是商店删卡的同类循环。
- 训练里这种闭环零奖励、零代价（γ=1、λ=0.99 下 SMITH 继承后续动作约 97% 的优势），训练本身压不住它。
- 今天的新主线加了"每个闭环扣 0.01"的训练期成本后，开/关 breaker 的差只剩 0.003，但闭环仍在训练期出现；宏动作环境是从结构上消灭它：没有取消路径，就没有闭环。

## 改了什么

- **候选表**：休息点开启升级选项时，原来的"SMITH（进子菜单）"一行被移除，替换为每张可升级的主牌组卡一行（`ChooseRestOption(A, B=d)`，A 为休息点选项，B 为牌组行号；B≥0 即宏动作行）；商店里合法的"删卡"一行替换为每张可删卡一行（`BuyEntry(A, B=d)`，价格照旧）。宏动作行排在该界面其他候选之后，按牌组顺序。
- **执行**：一个 env step 内完成"选项 → 选中该卡 → 确认"，中途状态校验不通过即 SIM_ERROR（fail closed）。C# 测试验证：状态哈希与手工三次点击完全一致；升级数恰好 +1；商店金币 = 原金币 − 价格，牌组 −1。
- **编码与模型规格不变**：没有新增 kind、buffer 或词表项；`encoder_version` 仍为 `3b73317739c650bd`，`ModelSpec` 开/关宏动作完全相同。因此**任何现有 checkpoint 可以直接带 `--macros rest,shop` 续训或评测**，不需要扩表。
- **默认关闭**：不传 `--macros` 时环境逐位与旧环境相同（有逐位一致性测试）。

## 信息对等

宏动作只暴露玩家本来就能看到、能合法点击的选项（可升级/可删除的卡），不泄露任何隐藏状态。

## 怎么用

训练（Colab 包 `sts2train-413f510188.tar.gz`，NativeAOT key `7aaa846a6a35`）：

```bash
bash run_train.sh RUN_DIR 12 2048 <你的训练参数> --macros rest,shop
```

评测：`sts2train eval --checkpoint X --seedset silent-a10-dev-v1 --policy greedy --breaker off --macros rest,shop`（checkpoint 的 config 里记着 macros 时评测默认沿用；`--macros none` 关闭）。

自检（训练期循环检测，只计数不干预）：开启宏动作后，`cycles.jsonl` 和 metrics 里的 `cycles_rest` / `cycles_shop` 应为 0；我们用 64 槽 × 300 步随机策略验证为 0，关闭时同一运行会出现闭环。

## 已知限制

- 牌组超过约 45 张时，商店的宏动作行可能超过训练器 64 行的候选上限，超出的行被截断并计入 `cand_over_max_rows`（有记录，未实测影响）。
- 休息点 SmithCount ≠ 1 的情况仍走原始提示流程。
- 真游戏联动（孪生运行器）尚未把"升级 X 卡"映射回真实游戏的三次点击，正在做；在此之前宏动作模型只能在模拟器里评测。
- v2（事件里的多卡变形/删除、限定可选卡种类的选牌、战斗内的手牌/牌堆选择）正在实现，目标同样是"一步完成、只提供可选项、无取消路径"；完成后 `--macros all`，AOT key 会变。
