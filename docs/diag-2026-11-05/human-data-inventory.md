# 人类对局数据盘点：能否给静默猎手 A10 加行为克隆（BC）辅助损失（2026-11-05）

## 结论

- **静默猎手 A10 的人类对局只有 1 局**（2026-11-03 那局，胜利，录像器 0.4.0，游戏 v0.111.0，15 个分段，读档 14 次）。
  这一局约 911 个人类决策：战斗内 740 个，战斗外 171 个。现有适配器（`sts2rec.human_dataset`）严格判定后，**能直接用于 BC 的有 617 个**：
  战斗 534 个，战斗外 83 个（地图 48、事件 20、休息 12、其他 3）。
- 放宽到静默猎手全部进阶共 23 局（13 胜），约 1.9 万个决策，其中适配器判定可用的约 1.15 万个。
  这 23 局里只有 5 局（A9 的 4 局、A10 的 1 局）带游戏原生存档锚点，能按房间对齐到模拟器；另外 18 局用的是录像器 0.2.0，没有存档。
- 0.4.0 的“选择前快照 + 候选列表 + `choice_index`”记录已经有了：3 局共 566 个决策，静默猎手 A10 那局占 272 个，全部是 `captured`，没有 `missing`。
  战斗内输入当时没有开这种捕获（`decision_capture_combat_inputs=false`）。
- **建议：现在不值得为 BC 开一个工程波次。** 一局 A10 数据作为训练信号太薄，更适合做“与人类选择的一致率”诊断集。
  要让 BC 可行，至少需要再录 30 到 50 局静默猎手 A10（其中胜局不少于 10 局），条件见第 4 节。

所有统计都在本机只读完成：单个 `python3 -I` 进程，`nice -n 10`，峰值常驻内存约 155 MB，逐行读取。
录像器根目录没有任何写入。sts2rec 包没有第三方依赖，脚本通过 `sys.path` 引入后在进程内调用。

几个口径需要先说明：

- **真实对局**：至少进过一个房间，并且至少有 5 个非自动决策。
- **MCP 污染**：任一分段的 manifest `mods` 含 `STS2_MCP`，整局排除。
- **自动动作**：`move_to_map_coord` 和 `ready_to_begin_enemy_turn` 不算人类决策，前者与 `vote_for_map_coord` 一一对应。
- **战斗内和战斗外**：`player_choice` 按选择前状态的 `state_type` 划分；`monster`、`elite`、`boss`、`hand_select` 算战斗内。

## 2. 0.4.0 决策记录与 `legal_actions`

- **0.4.0 决策记录确实存在，但只有 3 局、566 个决策**：静默猎手 A10 胜局 1 局，另外 2 局是 IRONCLAD A10 自定义模式。
  每个 `_decision.status` 都是 `captured / before_input`，没有一个 `missing`。
- `decision_audit` 只检查选牌、地图、事件和休息几类。在静默猎手 A10 那局里，检查过的 168 个全部通过。
  奖励、商店和地图移动不在检查范围内，`complete=null`。这表示没检查，不表示数据有问题。
- **战斗输入没有固定快照。** 3 局 0.4.0 的 `recorder_config` 都是 `decision_capture_combat_inputs=false`。
  所以出牌和结束回合用的是动作前最近的一张快照，而战斗中的轮询快照被限流到 800 ms。
  这正是战斗决策里有 155 个无法唯一对齐（`action_not_uniquely_aligned`）的主要原因。
- **`sts2rec canonical` 对旧数据同样输出 `legal_actions`**：全部 97,008 个步骤都有，包括 0.2.0 和 0.3.x。
  它是从 `state_before` 离线推出来的，与录像器版本无关。区别在于旧版本的 `state_before` 不是固定的选择前快照，
  而是动作前最近的一张快照。0.3.0 起奖励快照带候选卡，非战斗决策大多仍然能对上。
- **适配器的覆盖缺口跨所有版本，属于代码问题，不是数据问题**：奖励、`player_choice` 和商店在全部 141 局里可用数都是 0，
  全部因为 `action_not_uniquely_aligned`。
  适配器的 `_align_action` 目前不把录像器的 `reward_taken`、`player_choice`、`shop_purchase` 映射到 `legal_actions` 的命令词表。
  对 0.4.0 来说，候选列表和 `choice_index` 已经记录了，补这段映射是小工作量。
  另外，2 局 IRONCLAD 0.4.0 自定义局的战斗步骤全部是 `action_space_incomplete`，原因没有深查，与静默猎手无关。

### 3.2 对齐到训练器候选表（encoder `3b73317739c650bd`）：孪生已有的和还缺的

训练器的 BC 目标必须是：模拟器在同一状态下的观测缓冲区，加上一个 `cand` 行号（`RunSim.LegalActions()` 的顺序；奖励页是宏动作行
`TakeRewardCard` / `TakeRewardAlternative`；休息和商店可能是宏动作行）。录像器自己的状态 JSON 不能直接喂进这个编码器，所以每个人类决策都要在模拟器里重建出来。

**孪生已经有的**（`scripts/live/README-nn-twin.md`、`scripts/live/nn_twin/twin.py`）：

- 能从游戏的 `.save` 重新播种模拟器（`SaveEntry`，即 `RunImporter.FromSave`），并且已在房间开头、战后奖励和涅奥结束这几类锚点上验证过。
  录像器 0.3.1 起会把每个存档复制进分段的 `native/saves/`，并写一条 `run_saved` 事件（带 `anchor_kind`、层数和 `state_seq`）。
  静默猎手 A10 那局有 88 个存档，文件都还在。
- 能在模拟器候选行和游戏动作之间“按含义”映射：牌 id + 升级 + 目标 combat_id、地图坐标、奖励身份、商品、休息选项、
  多个卡牌奖励按名次配对，覆盖全部 23 种 `RunActionKind`。
- 同步检查已经成熟：E3 农场的每决策一致率是 99.5% 到 99.9%，真实游戏里 lockstep 跑过 0 desync。

**还缺的**：

1. **反向映射**：孪生的映射方向是“模拟器行 → MCP 动作 JSON”。BC 需要“录像器动作词表 → 模拟器行”。
   录像器的词表（`play_card.combat_card_index`、`reward_taken.set_index`、`player_choice.indexes` 等）和 MCP 的不同，需要新写一个适配层，
   宏动作行还要把录像器的“点开奖励 + 选牌”两步合成一个。
2. **离线重放器**：按存档锚点重新播种，然后在房间内逐步执行映射后的人类动作，每一步拿录像器快照和模拟器观测对比；
   一旦 desync，就丢掉到下一个锚点为止的数据。战斗中途没有存档，所以战斗内 desync 会损失这场战斗剩下的决策。
3. **读档分支处理**：要识别被回滚的分支。可以保留它（也是合法的人类决策，但玩家已经知道了结果），也可以丢掉。
4. **旧数据无锚点**：0.2.0 的 135 局没有存档，只能从种子开局整局重放。可是读档会改写 RNG 轨迹，
   118 局还在 v0.107.1（模拟器移植的是 v0.111.0），解锁状态也可能不同。这部分实际上很难用上。
5. **已知的导入限制**：带 `extra_rewards` 的战后存档会被拒绝；模拟器默认全解锁（重新播种后才用存档里的真实解锁）。
6. **训练端**：`sim/tools/train` 里还没有 BC 或辅助损失的代码路径，需要加 BC 项，并且要防止它冲掉 RL 已经学到的东西。

工作量估计（未验证）：第 1、2 项是这次的主体，大约是一个“孪生规模”的波次；适配器补齐奖励、选牌和商店映射是小工作量。

## 4. 建议

**就现在的数据量，不值得为 BC 开工程波次。** 静默猎手 A10 只有 1 局、约 900 个决策，而且是一局胜利、一副牌组、一条路线。
拿它做辅助损失或预训练，最可能的结果是记住这一局的牌组和路线，对 RL 卡在 0.44 的瓶颈没有可信的推动力。
战斗外决策（领卡、删牌、商店、路线）恰恰最可能是策略短板，但这部分只有 171 个，几乎为零。
把静默猎手低进阶的 23 局（约 1.9 万个决策）加进来，量还是比 RL 少 5 个数量级；而且其中 18 局是 0.2.0、没有存档，很难对齐，可用的只剩 5 局。

现阶段这批数据更合适的用途是：把静默猎手 A10 那局和 A9 的 4 局（都带存档锚点）对齐到模拟器后，做一个“人类一致率”诊断集，
看策略在关键非战斗决策（领卡、商店、路线）上和人类差多少。这只需要上面第 1、2 项的一个子集。

**让 BC 可行的条件**：

- 在 v0.111.0、录像器 0.4.0 上再录 **30 到 50 局静默猎手 A10 标准局**（其中胜局不少于 10 局），
  每局约 1,000 个决策，总共 3 万到 5 万个决策。
- 录制时打开 `decision_capture_combat_inputs=true`，让战斗决策也带固定的选择前快照。
- 不装 QuickSL，并尽量少读档。
- 同时补齐反向映射和离线重放器。

按每局约 1 小时算，需要 30 到 50 小时的人类对局时间。只有达到这个量级，才值得考虑 BC 辅助损失，而且优先放在战斗外决策上。

## 不能回答的问题

- **读档造成的重复和被回滚分支有多少**：没有逐项去重，表中的数字是原始记录数，是上界。
- **对齐成功率**：没有真正跑模拟器重放（本机禁止运行 dotnet 和 `sim/`），所以不知道这些人类决策里有多少能无 desync 地落到 `cand` 行上。
  孪生在 agent 对局里的 99.5% 到 99.9% 不能直接当作人类录像的对齐率。
- **人类决策质量**：不知道这些决策是否比当前策略更好。只有 1 局 A10，没有败局作对照，无法估计人类在 A10 的真实胜率；
  全部角色 A10 是 6 胜 / 25 负，但那是别的角色。
- **“放弃”的含义**：manifest 的 `abandoned=true` 可能是主动放弃，也可能是读档或退出的副作用，没有区分。
  “无结果”的局可能还在进行，也可能结束事件没录到。
- **IRONCLAD 0.4.0 自定义局战斗步骤全部 `action_space_incomplete`** 的原因没有查（不影响静默猎手结论）。
- **BC 对 RL 的实际增益**：这份盘点只回答数据量，不回答训练效果。
- **游戏存档目录里的历史局**（`unlock_profile` 显示存档累计 171 局、60 胜，比录像器录到的多）：录像器开始录制之前的局没有逐步记录，
  不能用于 BC；没有去读游戏存档。
