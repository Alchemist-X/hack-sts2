# Capacity of one Docker host: many environment instances, one command (2026-11-02)

User criterion 1.4 (docs/HANDOVER.md §1): many environment instances on one Docker host, started with one command,
with measured capacity. This page records the tooling and the numbers measured on Huginn.

**Summary.**

- `scripts/sts2_cluster.sh up N [--host raven]` starts N play servers (one container each, ports base..base+N-1 on
  the host's loopback) and waits until all answer `/health`; `status`, `urls`, `logs i`, `tunnel` and `down` manage
  them. `sts2eval run --urls a,b,c` runs one seed set over several servers (game *i* on server *i* mod N, recorded
  per game as `server_url`).
- The image now carries a NativeAOT `Sts2Sim.Vec.so` and `sts2vec` uses it by default inside the container:
  **62-63k env-steps/s** at 1024 or 4096 envs x 8 threads on Huginn, 2.4-2.8x the hostfxr path in the same image
  (21.8k / 26.7k).
- Play server, random policy, Huginn (8 vCPU, clients on the same host): **the host saturates at about 26-28
  random games/s (1,800-1,900 steps/s)**, whether that is 1 server with 8 clients or 8 servers with 1-2 clients each.
  One server process uses every core; more servers add isolation (crash domains, separate logs), not throughput.
  Server CPU per random game: 0.14 core-s unloaded, 0.22 core-s at saturation. Memory: **110-150 MiB per server
  container** under load, peak at most 193 MiB.
- LLM runner, random policy: one `sts2eval` process is CPU-bound at about **7 games/s** (one Python core) whatever the
  number of servers behind `--urls`; four runner processes over four servers reached 11.5 games/s. For an LLM
  policy the model latency, not the environment, is the limit (a Claude game takes minutes).

## Host

Huginn (`ssh raven`): linux/amd64, Intel Xeon Platinum KVM guest, 4 cores x 2 threads = **8 vCPU**, 30 GiB RAM,
Ubuntu 24.04, Docker 29.9 (data-root `/data/raven/docker`). Image `sts2sim:latest` built from `git archive` of this
branch (`68b9f20`, a pre-squash snapshot of this commit: Dockerfile, entrypoint, `.dockerignore` and all code
under `sim/` are identical; only `sim/BENCH.md` and a README line differ) under
`/data/raven/hack-sts2/tmp/huginn-scale/`. The host was otherwise idle (load 0.02) during the play, runner and vec
sections; another job (a gates run in its own container) started during the two extra runner rows at the end, which
are marked.

## Play server (HTTP, `sim_play.py random`)

Each client is `python3 sim/tools/play/sim_play.py random --runs 200 --seed <k*1000000+1> --url http://127.0.0.1:<port>`
(sequential, one request at a time, IRONCLAD, A0, `ported_only`), run on the host against the published ports.
Clients and servers share the 8 vCPU. CPU % is one `docker stats` sample of all server containers 8 s into the run.

| Servers | Clients per server | Games | Wall s | Games/s | Games/s per server | Games/s per vCPU | Steps/s | Server CPU % | Mem per server MiB (peak max) | Crashes |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| 1 | 1 | 200 | 26.9 | 7.43 | 7.43 | 0.93 | 513 | 105 | 126 (131) | 0 |
| 4 | 1 | 800 | 37.0 | 21.62 | 5.41 | 2.70 | 1,469 | 464 | 111 (139) | 0 |
| 8 | 1 | 1,600 | 61.2 | 26.15 | 3.27 | 3.27 | 1,780 | 597 | 120 (162) | 0 |
| 1 | 4 | 800 | 40.5 | 19.76 | 19.76 | 2.47 | 1,342 | 379 | 153 (162) | 0 |
| 1 | 8 | 1,600 | 60.5 | 26.45 | 26.45 | 3.31 | 1,800 | 576 | 144 (193) | 0 |
| 8 | 2 | 3,200 | 113.8 | 28.13 | 3.52 | 3.52 | 1,918 | 633 | 138 (167) | 0 |

Reading:

- One sequential client drives one server at 7.4 games/s (513 steps/s) and the server then uses about one core:
  **2.0 ms server CPU per step, 0.14 core-s per random game** (69 steps on average).
- Throughput tops out at 26-28 games/s for the host, the same for 1 server x 8 clients and 8 servers x 1-2 clients:
  the servers take about 6 of the 8 vCPU and the Python clients the rest. At saturation the server cost per game rises
  to 0.22 core-s (hyper-threads and client contention). With clients on another machine the servers alone would
  carry roughly 8 / 0.22 = 36 to 8 / 0.14 = 57 games/s on this host; that was not measured.
- Per server process there is no throughput reason for replicas (the server is multi-threaded, one lock per game).
  Use several servers for isolation, separate crash logs, different server flags (`-- --reveal-moves`), or to give
  each runner its own server.
- Memory is flat: 110-150 MiB per server under load, the highest peak 193 MiB (one server with 8 clients). 8 servers
  take about 1.1 GiB.

## LLM runner (`sts2eval run --policy random --urls ...`)

200 games (40 seeds x the 5 characters, A0, `ported_only`, seed set `capacity-a0-200`, generated by the capacity
script), `--concurrency 32`, `--obs-mode compact` (the default), the runner in the image on the host network:

| Servers (`--urls`) | Games | Steps | Wall s | Games/s | Steps/s | Games per server | Results |
| ---: | ---: | ---: | ---: | ---: | ---: | --- | --- |
| 1 | 200 | 13,622 | 29.4 | 6.81 | 464 | 200 | 200 loss, 0 crashed |
| 4 | 200 | 13,622 | 27.9 | 7.17 | 488 | 50/50/50/50 | 200 loss, 0 crashed |
| 8 | 200 | 13,622 | 28.9 | 6.93 | 472 | 25 x 8 | 200 loss, 0 crashed |
| 4, one runner process per server (50 games each, `--concurrency 8`)* | 200 | 13,622 | 17.4 (23.6 with 4 container starts) | 11.5 | 783 | 50 x 4 | 200 loss, 0 crashed |
| 1, `--obs-mode full`* | 200 | 13,622 | 30.6 | 6.54 | 445 | 200 | 200 loss |
| 1, `--obs-mode compact`* | 200 | 13,622 | 29.9 | 6.69 | 456 | 200 | 200 loss |

\* measured while another job's test run was using the host.

The same 13,622 steps in every row: the random policy is seeded per game, so the server a game runs on does not
change it (also asserted by `tests/test_urls.py`). One runner process sits at 100-110 % CPU (one Python core: JSON
parsing, rendering, transcripts) while its server uses about one core, so `--urls` alone does not speed a random
run up; several runner processes do. For a Claude policy a game takes minutes of model time, so one runner and one
server carry any realistic `--concurrency`.

## sts2vec (in-process, NativeAOT vs hostfxr)

`docker run --rm sts2sim:latest sh -c 'sts2vec bench --envs E --threads T --steps S --json && cat /sys/fs/cgroup/memory.peak'`
(pool 64, random policy, pool warmed before the timed window, 10 untimed warm-up steps; S = 500 at 1024 envs, 300
at 4096). Per thread = env-steps/s divided by the threads (the host has 4 physical cores, 8 hyper-threads).

| Library | Envs | Threads | Steps | Env-steps/s | Per thread | ms/batch | Buffers MB | Container peak MiB | SIM_ERROR / CONTENT_GAP |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| AOT | 1024 | 4 | 500 | 51,160 | 12,790 | 20.0 | 27 | 472 | 0 |
| AOT | 1024 | 8 | 500 | **62,109** | 7,764 | 16.5 | 27 | 457 | 0 |
| AOT | 4096 | 4 | 300 | 50,968 | 12,742 | 80.4 | 109 | 668 | 0 |
| AOT | 4096 | 8 | 300 | **63,141** | 7,893 | 64.9 | 109 | 671 | 0 |
| hostfxr | 1024 | 8 | 500 | 21,827 | 2,728 | 46.9 | 27 | 392 | 0 |
| hostfxr | 4096 | 8 | 300 | 26,655 | 3,332 | 153.7 | 109 | 661 | 0 |

- AOT in the container matches the native AOT row in `docs/linux-validation-2026-11-01.md` (61,425 at 1024 x 8).
- About 12.8k env-steps/s per physical core; the hyper-threads add about 22 % (4 -> 8 threads).
- AOT starts at full speed; the hostfxr rows in a 300-500 step window are mostly tiered-JIT warm-up (the C#
  steady-state bench reaches about 51k at 3000 steps). For training jobs in the container, the AOT default is the
  right one; the hostfxr path stays for debugging and for images built with `VEC_AOT=0`.
- Memory: 0.45-0.67 GiB per process at 1024-4096 envs.

## Exact commands

```bash
# on the Mac: ship the commit and build on Huginn
git archive --format=tar.gz -o hs.tar.gz HEAD
scp hs.tar.gz raven:/data/raven/hack-sts2/tmp/huginn-scale/
ssh raven 'cd /data/raven/hack-sts2/tmp/huginn-scale && mkdir src && tar xzf hs.tar.gz -C src && cd src &&
           nohup docker build -t sts2sim:latest --build-arg STS2SIM_VERSION=68b9f20 . > ../build1.log 2>&1 < /dev/null &'
ssh raven 'docker run --rm sts2sim:latest vec-check; docker run --rm -e STS2VEC_AOT_LIB= sts2sim:latest vec-check'

# cluster from the Mac
scripts/sts2_cluster.sh up 2 --host raven --base-port 18765
scripts/sts2_cluster.sh status --host raven
scripts/sts2_cluster.sh tunnel --host raven &
uv run --project sim/tools/eval sts2eval run --seedset a0-s10 --policy random --concurrency 10 \
    --urls "$(scripts/sts2_cluster.sh urls --host raven)"
scripts/sts2_cluster.sh down --host raven

# all tables above (on Huginn, in the unpacked tree): play (6 configs), runner (1/4/8 servers), vec (AOT + hostfxr)
bash scripts/cluster_capacity.sh ../cap all      # ~10 min; knobs: PLAY_CONFIGS, RUNS, RUNNER_SERVERS, VEC_CONFIGS, ...
```

The two extra runner rows: four `docker run --rm --network host --user $(id -u):$(id -g) ... sts2sim:latest eval run
--seedset /data/part<k>.json --policy random --concurrency 8 --url http://127.0.0.1:<18765+k>` in parallel against
`sts2_cluster.sh up 4 --name capacity`, the seed set split 4 ways (`games[k::4]`); and one runner with `--obs-mode
full` / `compact` against one server, its CPU read with `docker stats --no-stream`.
