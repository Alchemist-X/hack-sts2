## 6. 不预设 PPO：按瓶颈选算法

算法与环境是两个独立决策：重写模拟器不意味着必须用 AlphaZero，保留真实引擎也不意味着必须用 PPO。下列是候选，不是推荐全部实现。

| 候选 | 适合检验的条件 | STS2 中的主要问题 |
|---|---|---|
| BC + 价值网络 | 有强教师/玩家轨迹，想先得到可用初始策略 | 教师质量与状态覆盖；当前弱教师不够；动作一致率不是胜率 |
| 候选 Q 网络 + replay（Double/Distributional DQN 思路） | 环境采样贵，希望复用已有交互 | 需要可变合法候选 Q(h,a)、记忆、终局传播、目标网络；不是把固定 Atari 动作头直接套上 |
| IQL / 离散 CQL + 后续在线改进 | 有覆盖良好的离线数据，希望降低新增交互成本 | 离线分布外动作价值、数据质量；当前全败数据不提供充分通关信号 |
| PPO / V-trace 路线 | 能稳定提供大量新轨迹，结构化策略容易批量推理 | 新样本需求、长局信用分配；已有代码只是降低对照实验成本 |
| 搜索 + 策略/价值蒸馏（Expert Iteration 思路） | 有准确、可廉价分支的规则模拟器 | 随机性、部分可观测、搜索预算和长局分支；搜索得到强标签后蒸馏到快速网络 |
| 学习世界模型 + 规划 | 精确模拟器代价很高、真实交互昂贵 | 稀有卡/遗物组合、规则和合法性误差会被规划放大，研发复杂度更高 |

PPO 对当前采样批次做多轮优化，不是“样本只能用一次”；区别在于不能把很旧的任意 replay 无条件当当前 on-policy 数据。[PPO 原论文](https://arxiv.org/abs/1707.06347)

IQL 与 CQL 是可研究的数据复用方向，并不证明它们已在 STS2 胜过 PPO。[IQL 原论文](https://arxiv.org/abs/2110.06169)、[CQL 原论文](https://arxiv.org/abs/2006.04779)。DQN 路线参考 [Rainbow 原论文](https://arxiv.org/abs/1710.02298)，但要为变长候选和公开历史改造。

搜索生成更强策略、网络学习并反过来指导搜索，是 [Expert Iteration](https://arxiv.org/abs/1705.08439) 的基本思路。原实验是 Hex，不能直接外推 STS2 的预算或胜率。STS2 是单人随机、部分可观测任务，没有必须对抗自博弈的要求；不能把真实隐藏牌序交给 AlphaZero 式完全信息搜索。

建议评审给出**一条主线和一个最小对照**，以相同真实环境交互预算、墙钟和成本比较独立胜率；不以训练 loss 或已写代码量决定赢家。若选择离线方法，明确需要新增多少、什么质量的数据；若选择搜索，明确每个决策的分支预算及最终部署是否保留搜索。

## 7. 从零重写：需要评估的具体范围

合理的最小目标是“STS2 规则级训练环境”：状态、合法动作、状态转移、随机机制、终局与奖励。训练不需要画面、声音、Steam UI、动画或联机。保留现有真实游戏桥用于规则对照和最终部署，已有工程并不因此作废。

| 环境路线 | 可能收益 | 需要验证的风险 |
|---|---|---|
| A. 继续优化真实 headless 引擎 | 覆盖现有规则，较低迁移风险 | UI/异步/场景/帧等待是否仍限制吞吐 |
| B. 抽取/移植原有 C# 规则，替换宿主与表现层 | 尽量复用规则实现，去掉引擎调度 | 静态单例、资源、Godot 类型、异步选择与全局 hook 耦合；不能靠空 stub 跳过规则 |
| C. 从零实现数据驱动的规则模拟器 | 可设计廉价 clone、分支、批量训练接口 | 触发顺序、舍入、目标选择、随机分布、全部角色/内容和组合正确性；模型会利用模拟器缺陷 |

模拟器接口至少需要：

- `reset(config)`、`observe(history)`、`legal_actions()`、`step(action)`、`terminal()`；决定以游戏规则动作还是现有 UI 操作作为训练步。
- 可复制模拟器内部状态供训练分支，但策略只获得 `observe` 的公开信息。未来随机结果不能进入特征或教师标签。
- 未知抽牌/随机目标按公开条件分布采样；供搜索使用的分支不能偷取真实对局隐藏状态。模拟器内部拥有随机状态，与把它暴露给模型，是两回事。
- 实例 ID、重复卡、升级/附魔、费用变化、伤害舍入、格挡、死亡与触发顺序、强制选择、药水/遗物 hook 等要有明确定义。
- 地图、奖励、商店、事件、休息点、战后持久状态与进阶修正同样属于全局策略环境。
- 若模拟器一步直接完成规则决策，而真实接口还要打开预览/点击确认，必须定义语义动作到实际界面操作的确定性适配；适配器不能额外替策略选择。

**建议先评审一个受限原型，而不是立即承诺完整重写：**

1. 先战士战斗核心，覆盖常见出牌/结束回合、状态触发、抽弃耗牌、多目标、一个嵌套选牌；明确允许哪些卡、遗物和敌人，不把子集成绩当全游戏成绩。
2. 路线 B 与 C 选同一小范围做可行性比较；由评审判断需要做一个还是两个原型，不要求先开发数百张卡。
3. 用真实引擎作为参照验证确定性转换、候选与终局；随机部分比较条件分布/公开结果，不因没有相同隐藏种子就假装逐步一模一样。更强的受控随机测试如需新的测试注入能力，先说明边界，保持与玩家策略完全隔离。
4. 记录未实现机制和首次分歧；遇到不支持规则明确停止或走声明过的路径，禁止静默当空操作、删候选或更改奖励。
5. 测量单进程规则步、公开观察+合法候选、clone、完整战斗 reset、批量 rollout 的各自吞吐与内存；不能只报 `step()` 空循环。新旧步粒度不同，还要比较相同战斗/完整对局耗时。
6. 原型证实规则正确性与明显吞吐收益后，再按角色与机制扩展。现有 100–500 动作/秒目标、任何“万步/秒”猜测都不能替代实测。

旧规划把完整纯逻辑环境称为月份级工作，只是粗粒度判断。**评审应根据依赖审计和原型推翻或重估它**；不要把既有 2–4 个月、1,000 万—1 亿样本、$2,000–10,000 当可靠预测。

## 8. 预算、指标和最终验收应该怎样重估

现有 Modal 价格情景（上轮查询值，非报价承诺）：A10 learner +4 CPU+16 GiB 约 $1.42/小时，H100 同配套约 $4.27/小时；32 物理核等效+64 GiB 约 $2.02/小时。采样池的 Modal 游戏容器尚未验证。这些费率不要与 Huginn 的逻辑核数混用；若预算依赖现价，应查 [Modal 价格](https://modal.com/pricing)。

现有数据首先说明采样主导，小 learner 暂不需要长期 H100。后续按每个角色的独立胜率增量/百万真实交互、有效样本/美元、完整对局墙钟和工程成本做取舍。搜索展开节点与真实环境动作必须分别计数。

最终评估建议保留未参与训练调参的新对局，每角色 500–1,000 局作为样本量占位，并计算置信区间、五角色同时声明的校正。评审可以重新设计样本量；核心是不能把“观察到略高于 50%”说成有把握真实超过 50%。环境故障、策略循环、超时、中断均保存并分列；正式成绩不能选择性删失败。

部署时使用同一公开状态/候选语义，本地 CPU 常驻推理。现有 H100 权重的 390 状态离线 IPC P99 约 2 ms，实际 62 动作 P99 7.56 ms；更大网络和带搜索模型必须重新测。渲染帧时、游戏线程状态采集、网络推理是不同指标。
