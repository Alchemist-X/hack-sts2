## 为什么用了 Mac，训练是否必须上云

本机游戏用于跨平台交付验收：服务器或 GPU 训练的权重，能否由 Mac 的 CPU 推理器加载，并对真实游戏完成动作。它不是采样主机的必要组成部分；常规训练可以完全在 Huginn 完成，不占用用户电脑上的游戏。

当前路径是 Huginn CPU 跑游戏和逐步推理，Huginn CPU 或云端 GPU 做成批参数更新，返回新 checkpoint。部署只需要本地 CPU 模型，不逐动作请求 Modal。现有 Modal SSH 桥由本机发起，若要求电脑休眠也能持续云端训练，尚需迁到批准的常驻调度位置并按运维约定配置私有凭据；不能将本机凭据复制到共享数据盘。全 CPU 训练没有这个依赖。

以后 Google 服务使用用户指定的 **`issue` 账号**，先核对身份、计费项目和权益。此前 Colab T4 用的是另一个已登录账号，不代表 issue 账号的资源可用性。Colab 配额、卡型和会话寿命会变化，适合交互实验；连续无人值守的训练优先现有 Huginn、Modal 或有明确配额的 GCP 作业。[Google 官方 FAQ](https://research.google.com/colaboratory/faq.html)

## 目标和验收口径

建议固定游戏版本、全解锁条件、单人规则和完整自然通关定义；每个角色单独统计：Ironclad、Silent、Regent、Necrobinder、Defect。不得用五角色平均胜率代替每个角色 >50%。无 SL，不读取隐藏 RNG、未公开牌序或未来分支。

先以每角色 100 局作开发验证；最终冻结模型，每角色 500–1,000 个未参与调参的新对局，报告胜率及置信区间，对五角色同时声明做多重比较校正。目标应留有余量，例如观察胜率约 60%，再检验每个角色置信下界是否超过 50%。100 局 51 胜并不能证明真实胜率超过 50%。

策略卡循环、超时、主动放弃属于部署失败，不能从分母删掉来提高胜率。环境故障单列并阻断正式验收；用户暂停中断单独记录，不当作自然战败。开发评测可以频繁做，最终保留测试集不能反复调参。

这是约 6–12 周以上的研发计划，按 2–4 个月留窗口更稳妥；不是承诺到期达到目标。当前没有赢局学习曲线，无法可信地给出保证成功的总样本数和总金额。若阶段 3 长期停滞，应停扩容并回查表示、教师、奖励与信用分配。

当前 21 万参数哈希 MLP 用于验证接线，候选之间和牌之间的关系表达有限。下一版建议试 100 万–1,000 万参数的实体编码/注意力网络，包含角色标识和该角色公开资源、牌堆无序集合、敌人意图、药水与遗物机制；为公开历史提供轻量记忆。参数范围只是实验起点，未证明必须这么大。共享主干按角色条件化，必要时分头；若统一模型产生负迁移，先训练专用模型再蒸馏为统一模型。

教师数据先从每角色约 100–300 局高质量完整轨迹和关键局面纠错起步，训练/验证按整局与来源切分；数量不是充分条件。当前 60 局教师没有通关记录，继续纯模仿它不能当作高水平策略来源。可结合合法取得的熟练玩家轨迹、规则规划器和基于公开信息的搜索教师。搜索不得复制真实隐藏 RNG 或读取未来来选动作；未知抽牌只能按公开信息建立分布。最终策略尽量直接推理，昂贵搜索用于教师或训练阶段。

PPO 作为已有实现的对照，不预设为最终主线。应比较可复用数据的候选 Q 网络、IQL/CQL 等离线改进，以及准确模拟器支持的搜索教师与蒸馏。把完整通关作为主要目标，检查现有楼层、血量等奖励是否诱导刷分；若增加塑形，优先可验证的势函数差并处理终局边界。检查长局折扣、价值训练和跨截断 bootstrap，不能照搬小 pilot 超参数。成功轨迹过少时先加强教师或课程，不把更多 GPU 当作学习信号。

## 采样瓶颈怎样处理

1. 分解墙钟：游戏推进、主线程状态采集、JSON/IPC、开局/reset、CPU 推理、learner 更新各占多少；用完整战役有效决策/秒和故障率作主指标。
2. 先完成常驻 actor、自然终局 reset、错峰开局、静态规则缓存、精简结构化状态、减少轮询与日志开销。保留审计能力，不通过漏掉候选提高数字。
3. 评估直接调用规则/动作队列的接口，减少对 UI 节点和帧等待的依赖。对每类交互与真实引擎比较公开状态、合法动作、奖励与终止结果。
4. 若剖析仍显示 Godot/界面调度占主导，再提取战斗逻辑内核，逐步覆盖房间。完整五角色纯逻辑模拟器是独立的大工程，不能按改几个动画等待估计；先做 1–2 周可行性探针，再估剩余月份级工作量。
5. 在稳定版本上扩 CPU actor；当前 Huginn 4→8 进程预热战斗只约增 7%，继续加进程不会成倍提速。云 CPU 游戏容器尚未验证，必须先做小规模单机验证与 4/8/16/32 actor 扩展曲线。

阶段性目标可设合计 100–500 个有效决策/秒，但**这尚未实测**，也不保证仅增加 CPU 就能达到。不能提前用它向用户承诺训练周期。

## 部署验收

每次训练导出使用同一编码/schema 和候选定义，在 CPU 重放公开观察，再进入隔离游戏验收。H100 返回权重已在 Mac 的 390 状态离线重放中取得 IPC P99 约 2.00 ms、零超时；实际隔离游戏 62 个动作 P99 7.56 ms，之后按用户暂停中止。这不能保证后续更大网络具有相同延迟。

目标可以设本机模型+IPC P99 <20 ms，游戏线程状态采集预算单独测；真实可见游戏比较无模型、模型空闲、模型执行三个条件的帧时。网络常驻外部进程，预热模型，不逐动作加载权重、不访问云端。过期动作或推理超时暂停，不能擅自出牌兜底。验收通过前不承诺“任何场景都不卡顿”。

暂停后的恢复入口是先读本文件、检查当前进程/容量和账单，再由用户恢复指令确定下一阶段；不自动执行历史驱动脚本。
